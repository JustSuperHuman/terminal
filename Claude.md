## Build And Run

- One-command local update:
  - `bun run update`
  - This restores NuGet packages, builds `Terminal\CascadiaPackage` as Debug x64, registers the loose `WindowsTerminalDev` package, installs a per-user `wt.exe` shim, and launches it.
  - Before registering, the script stamps a unique timestamp-based version into the generated `AppxManifest.xml`; re-registering the same version can fail with 0x80073CF6/0x80070020 when Windows cannot delete the previous registration's stale AppRepository metadata directory.
  - Re-registration removes the existing `WindowsTerminalDev` package registration first, clears the generated loose-package output directory, and preserves app data when the host supports it; this avoids the same-version dev package registration block and stale package output locks.
  - Use `bun run update -- -NoLaunch` to build/register without launching.
  - Use `bun run update -- -MakeDefault` to also set `WindowsTerminalDev` as the per-user default terminal application.
  - Use `bun run update -- -NoWtShim` to skip replacing `wt.exe` command resolution.
  - Use `bun run update -- -Pull` only when the working tree is clean and you want a `git pull --ff-only` before building.
- Launch without building:
  - `bun run launch` (`tools\launch-dev-terminal.ps1`) starts the existing `WindowsTerminalDev` build; use it instead of `bun run update` when nothing needs rebuilding.
  - It runs the built exe through the `wtd.exe` execution alias in `%LOCALAPPDATA%\Microsoft\WindowsApps` — that alias is what supplies package identity — and falls back to `shell:AppsFolder\WindowsTerminalDev_8wekyb3d8bbwe!App` when the alias is missing. The dev loose layout has no `wt.exe`; `wtd.exe` is the commandline entry point.
  - Trailing args go to `wtd.exe` untouched: `bun run launch -- new-tab -d F:\terminal`.
  - `-Restart` kills running dev instances (matched by exe path, so the Store package is untouched) before launching; `-NoRegister` refuses to register instead of doing it; `-Direct` runs the loose-layout `WindowsTerminal.exe` with no package identity (debugging the launch itself only — Terminal normally fails that way).
  - The script parses those switches by hand out of `$args` instead of using `param()`. PowerShell prefix matching binds wt's own `-d <dir>` to a `-Direct` switch and silently drops the flag, and a literal `--` separator fails parameter binding outright.
  - Missing `src\cascadia\CascadiaPackage\bin\x64\Debug\WindowsTerminal.exe` is a hard error pointing at `bun run build`; a missing package registration is repaired in place (see below).
- `bun run register` (`tools\register-dev-terminal.ps1`) is the register step factored out of `update-dev-terminal.ps1`: copy `res\terminal\images-Dev` into the layout's `Images`, stamp a unique version into `AppxManifest.xml`, `Add-AppxPackage -Register`. Both `bun run update` and `bun run launch` call it, so the version-stamp and image-copy rationale lives in one place.
  - Building `Terminal\CascadiaPackage` rewrites the generated `AppxManifest.xml` back to source version `0.0.1.0`, which drops the existing loose-package registration — after a plain `bun run build` the app cannot launch until it is registered again. `bun run launch` detects the missing registration and re-registers the layout on disk rather than forcing a full rebuild.

Delete that project's `obj` directory (not `packages`) and rebuild; the `.tlog` files with `G:\` are harmless.

## UI Notes

- This is native product UI. Preserve existing WinUI controls, resource usage, keyboard/accessibility behavior, and theme-aware brushes.
- Keep tab behavior attached to the existing tab model and action dispatch. Avoid creating a parallel tab state.
- Prefer changing `TabRowControl`/`TabHeaderControl` layout before touching pane/session logic.
- Search UX should use standard XAML input affordances, live filtering, and keyboard navigation; avoid custom drawing unless necessary.
- Current vertical-tab prototype keeps the original `mux:TabView` collapsed as the behavioral backing control and renders tabs through `TabRowControl.FilteredTabs`.
- Vertical-tab selection is bridged through `TabRowControl::VerticalTabSelected` into `TerminalPage::_SetFocusedTab`; `_SetFocusedTab` and tab initialization now call `_UpdatedSelectedTab` directly because the collapsed backing `TabView` cannot be relied on to populate the center `TabContent`.
- Launch/window sizing for the rail is currently hard-coded at 240px in `TerminalWindow.cpp`; matching visual width is on `TabRowControl.xaml`.
- The vertical rail background is driven by `TerminalPage::_updateThemeColors()` assigning `TitlebarBrush()` to `_tabRow.Background()`, so acrylic/custom tab-row themes stay on the rail even when the collapsed backing `TabView` is not in the titlebar.
- Vertical tab search tokenizes whitespace terms and searches title/profile/path metadata first, then command history/quick fixes and the last 32K chars of terminal buffer text for queries with at least two typed chars when metadata does not match.
- Collect-windows is **gone** (was: a rail button routing `TabRowControl -> TerminalPage -> TerminalWindow -> AppHost`, a `ContentDialog`, `TerminalPage::SendAllTabsToWindow`, and an `EnumWindows()` sweep in `AppHost.cpp`). The whole chain was removed rather than left dangling behind a hidden button; `git show 9932f8cc4` and `86eb437f8` have it if it is ever wanted back. Worth keeping from it: external terminal windows can be *found* but never live-moved, because `ControlInteractivity`/ConPTY content IDs are process-local and Windows exposes no safe handoff for already-running terminal apps, other WT packages, or elevated sessions - so do not rebuild that half.
- The elevation shield sits in the rail's search row, not a row of its own. On its own row it cost every elevated window a full line above the tab list for the entire session. The row below the search box survives only as the collapsed anchor `WorkspaceFlyout` opens at.
- The rail's "All" view is a directory tree, T3 Code style. `TabRowControl::_sectionRootForTab` picks each tab's section root as the highest of its bridge `ProjectPath`, its `Tab.GitRoot` and its live cwd that still contains the cwd, never a drive/UNC root or `~` (`_isGenericRoot`) unless the cwd is that root itself; so `F:\repo\src` joins the `F:\repo` section without a tab open at the repo root. `_bucketTabsByPath` then nests a section whose directory sits inside another section's directory as a subheading (`Parent`/`Depth`; `J:\Projects\instagram` stays its own project under a `J:\Projects` section instead of dissolving into it) — but never under a generic-root section, which stays flat. Header `Path` is the full display path at depth 0 and the path relative to the parent when nested; counts and strip rank flow up to parents; siblings sort by strip order then name; two top-level sections with the same leaf name get their parent folder prefixed. `TabGroup.Depth` drives `HeaderMargin`/`NameFontSize`, `Tab.RailDepth` drives `RailPadding`, and `TabGroup.Directory` is the raw path the header [+] opens (`NewTabInDirectoryRequested`). Collapsing a header hides its whole subtree (`TabGroupBucket.HiddenBy`); a *change* of focused tab into a hidden subtree reopens it, but `_syncListSelection` during a rebuild never does. A grouped `CollectionViewSource` was tried first and rendered nothing: XAML cannot enumerate a C++/WinRT `IIterable<Tab>` group. Drag-reorder is off whenever the list is grouped.
- Tab working directories are **event-driven off shell integration**, with a process walk only as a fallback. Ranked: (1) the shell reports OSC 7 / OSC 9;9 -> `Terminal::SetWorkingDirectory` fires `_pfnWorkingDirectoryChanged` (only when the directory actually moved) -> `ControlCore::WorkingDirectoryChanged` -> `TermControl` bubbles it -> `TerminalPage::_ControlWorkingDirectoryChangedHandler` refreshes that one tab immediately; (2) `ConptyConnection::ForegroundWorkingDirectory()` reads `CurrentDirectory.DosPath` from a PEB; (3) the profile's starting directory. `control.WorkingDirectoryFromShell()` distinguishes (1) from a control still holding its pre-seeded starting directory, and the fallback never overrides a shell report.
- **pwsh cannot be tracked from outside.** `Set-Location` moves the PowerShell provider location, not the process cwd the PEB holds, so a pwsh tab that has not reported looks like it never left its launch directory. That, plus a stale dead reference to a script in package `LocalState` that re-registering deletes, is why `cd` used to do nothing. `TerminalPage::_installShellIntegration()` now keeps a marker-delimited managed block at the end of `Documents\PowerShell\Microsoft.PowerShell_profile.ps1` and the `WindowsPowerShell` equivalent (current-host profile = loaded last, so it wraps oh-my-posh/starship rather than being clobbered by them). It runs once per process off the UI thread, is idempotent, strips the old `path tab color` block, only writes when content differs, writes atomically via a `.wt-new` sibling with a UTF-8 BOM, and is gated on the `shellIntegration.autoInstall` global setting. The block wraps the existing `prompt` and refuses to capture itself (matching `__WTPromptInner` in the body), which otherwise recurses into an escape-sequence-only prompt.
- The PEB fallback picks the **shallowest** descendant that reads back, not the deepest, and ignores descendants younger than 1500ms. The program the user ran is the ConPTY client's own child; what that agent then spawns (a tool-call shell, a test runner) sits below it, and preferring the deepest is what made tabs jump between rail sections and back as those came and went. `ConptyConnection::_processTable()` caches one `CreateToolhelp32Snapshot` for 750ms across all tabs and both walks (`ForegroundAgent` too) instead of one full ~600-process snapshot per tab per refresh.
- `_gitBranchForDirectory` is a directory-keyed cache revalidated against `.git/HEAD`'s write time (2s window), so the steady state is one stat rather than a parent-chain probe per tab. `_RefreshTabDirectory` coalesces: it drops out when a refresh is already in flight, or when the shell-reported cwd already matches `Tab.WorkingDirectory` and one ran within 2s. That matters because `_UpdateTitle` asks for a refresh on **every** title change, and a repainting TUI re-emits its title constantly - which is why merely focusing the window used to trigger visible rail churn.
- The 3s `_directoryRefreshTimer` sweep is now only for what events cannot cover: shells with no integration, TUI agents that never report, and branch changes made outside the terminal (which move no directory at all).
- The rail `ListView` has an **empty** `ItemContainerTransitions`. `AddDeleteThemeTransition`/`ReorderThemeTransition` animated every regroup, so a directory change - or a flap - read as the UI sliding around on its own.
- Working-tree line endings matter: `.gitattributes` sets `* -text`, so files are stored as-is and the repo's C++ is CRLF. An editor/tool once rewrote `ControlCore.*`, `TermControl.*`, `Terminal.*`, `TerminalApi.cpp` and `ICoreState.idl` as LF, which turned a 28-line change into an 11,948-line diff. Check `git diff --stat --ignore-all-space` against plain `--stat` before believing a large diff.
- New terminals inherit the focused tab's directory: `TerminalPage::_MakePane` fills an empty `NewTerminalArgs.StartingDirectory` from `_InheritedStartingDirectory()` (focused tab's live cwd, else its process-derived `Tab.WorkingDirectory`, else the selected project's cwd) for a brand-new pane (not duplicates/attached content/explicit `-d`). The old blanket `_activeProjectCwd` override in `_CreateConnectionFromSettings` is gone — it also clobbered explicit directories from the rail [+].
- `_UpdateTabView()` ignores fullscreen (and the `showTabsFullscreen` setting): the vertical rail is the only tab surface, so it stays visible in fullscreen and focus mode is the chrome-free view. When hidden, the whole `VerticalTabPane` (rail + resize handle) collapses — collapsing only `TabRow` leaves an empty fixed-width strip — and the project strip collapses in focus mode only.

A named mutex makes one WT process the spawner with a 15s respawn throttle; non-owners retry acquisition every pass and never hold a handle, so the spawner role fails over when the owning WT exits.
- The server records where it actually listens in `tools/terminal-web/.terminal-web-server.json` (pid/host/port, removed on clean exit); `TerminalBridge::_connectAny()` tries last-good port, then the default, then the recorded port, so a drifted port (default taken by a foreign process) doesn't read as offline. `GET /api/health` returns `{ok, pid, port, startedAt, sessions}`.

That is where `.terminal-web-server.json` and `.terminal-web-token` actually land, and the literal `%LOCALAPPDATA%\TerminalWeb` may not exist at all. Look in `LocalCache\Local` before concluding the host never started. `bun run launch:next` sets `TERMINAL_WEB_DATA_ROOT` explicitly, so the Next build's root is real.

It is either the ~2s startup window before the owner mutex is claimed and the listener bound (`_bridgeStatusTimer` polls every 2s), or a peer that cannot reach the recorded owner. Check the live title and `GET /api/health` before assuming the host failed.

Precedence in `terminalAgentSummaryMetadata`: OSC handshake > `screen` fingerprint > launch `command`/`profile`; screen outranks the launch command because a `pwsh` tab that later ran `claude` is an agent terminal and a `claude` tab that exited back to its shell is not.

- Agent-aware composed input (for driving Claude Code / Codex from a phone). The host answers three questions about any session from its already-rendered headless screen — no probing: `GET /api/sessions/:id/input-context` (`server/session-input.ts`: which agent is listening, whether it is mid-turn, the VT modes, and any menu it is blocking on), `GET /api/sessions/:id/commands` (`server/slash-commands.ts`: the agent's built-ins plus `.claude/commands` / `~/.claude/commands` / `~/.codex/prompts`, frontmatter descriptions included) and `GET /api/sessions/:id/files?q=` (`server/file-search.ts`: fuzzy lookup under the cwd, `git ls-files` fast path, bounded walk otherwise). `POST /api/sessions/:id/compose {text,submit,mode}` delivers a whole message: bracketed paste when the program takes one, paced chunks, then Enter after a settle delay.   - Agent detection scores screen fingerprints (Claude's `shift+tab to cycle` footer, Codex's `› ` prompt and model line) above the launch command, because an agent that exited back to its shell must stop being treated as an agent. `shell` is the whole command line for bridged sessions, so the executable is parsed out with the quotes/args stripped.

  - A menu only becomes one-tap replies when an entry carries a selection caret (`❯ 1. Yes`). Without that rule any agent answer ending in a numbered list would offer bogus replies.

- Rust-host projects (`rust-bridge/src/projects.rs`, wired in `host.rs`): `GET /api/projects` is saved projects plus one automatic project per live running session cwd (id `directory-<sha256(cwdKey)[..24]>`, stable across restarts), so a tab in any directory always yields a strip entry once the host knows the cwd. Native forwards live cwd changes through `ConptyConnection::UpdateBridgeCwd` -> `TerminalBridge::ForwardCwd` -> `tbr_update_cwd` (peers relay a `cwd` bridge message); `reconcile_projects()` also stamps `projectId` on sessions and broadcasts `projects` when the list changes. `PATCH /api/projects/:id {name}` renames (saved or automatic) and the name is remembered per directory in `.terminal-web-projects.json` (`{projects, names, order}`; Node-style `recents` is also read), `PATCH /api/projects/order {ids}` persists strip order, `GET /api/projects/recent` returns the remembered directories. `POST /api/projects` reuses the automatic id for that directory so filtered tabs keep their project when it becomes saved. The Node server got a matching `PATCH /api/projects/:id` (promotes automatic -> saved via `create()`).
- Native project strip: right-click (or double-click) a project tab for Rename/Close; rename opens a `Flyout` text box and PATCHes the bridge, updating `_bridgeProjects` locally without waiting for the poll. `Tab.ProjectName` (observable) is shown under the title in the rail next to the git branch; `_ApplyProjectNames()` refreshes names and pushes both into `TabRowControl::SetSectionNames`/`SetSectionOrder`, keyed by normalized directory. Drag-reorder in the rail is disabled whenever that grouping changes the window order (the drop index maps straight onto `_tabs`). `_projectServerRequest` and the globe button resolve host/port from `ConptyConnection::BridgeEndpoint()` instead of hard-coding 10001.
- **The project strip is the rail's headings.** `TabRowControl` publishes its top-level sections (`RailSection{Key,Name,Directory,Count}`, `RailSections()`, `RailSectionsChanged`) computed from *all* tracked tabs (never `visibleTabs`, which the search box and the active filter have already narrowed), only `Depth == 0` buckets, fired only when the set actually differs and behind a re-entrancy guard. `TerminalPage::_RebuildProjectTabs` renders "All" plus one chip per section, in rail order and mirroring each heading's count, so the two lists are 1:1 by construction; a saved bridge project with no live terminal simply has no heading and therefore no chip. The strip's key is a section key (`dir:<normalized path>`, or `section:none` for the "no directory" heading, whose group key is empty and would otherwise collide with "no filter"), and filtering is containment-aware (`SectionContainsTab` uses `_pathIsUnder` as well as equality) so selecting `J:\Projects` keeps the tab in `J:\Projects\instagram` that the rail nests under it. A filtered view stays *grouped*, so the chip and its heading read as one object - which also means rail drag-reorder is off in every non-search view. The bridge still supplies section **names** and **order** (merged by directory), never membership; a rename with no saved project behind it POSTs one to `/api/projects`, and applies locally first (`_sectionNameOverrides`, retired once the bridge agrees) so it works with the bridge offline. `_activeProjectId`/`_activeProjectCwd` are now *derived* from `_activeSectionKey` by `_UpdateActiveSectionTargets()`.
- Side-by-side test build: `bun run launch:next` (`tools/register-dev-terminal-next.ps1`) stages the Debug loose layout into `artifacts\WindowsTerminalDevNext-x64-Debug` (no PDBs), rewrites the manifest to identity `WindowsTerminalDevNext` / alias `wtdn.exe` and strips the COM handoff, app-extension and Explorer context-menu registrations, registers it without shutting down `WindowsTerminalDev`, seeds settings/state from the everyday package on first registration, and launches through the alias with `TERMINAL_WEB_DATA_ROOT=%LOCALAPPDATA%\TerminalWebNext`. The Rust owner mutex is derived from the data root (`owner_mutex_name`; the default `...\TerminalWeb` root keeps the legacy name), so the Next build runs its own bridge host on the next free port instead of joining the old terminal's host as a peer, which would otherwise hide new host-side features (project synthesis, rename) until the old terminal exits. Re-running the script stops only processes running from that staging folder. `WindowEmperor::HandleCommandlineArgs` mixes the package family name into the single-instance window-class/mutex key for packaged builds, so a differently named package is its own instance instead of handing its command line to the running `WindowsTerminalDev` (which is what made `wtdn` merely open a tab in the old window).
- Session restore: `firstWindowPreference` now defaults to `persistedLayoutAndContent` (`MTSMSettings.h`), so closing the last window persists tabs/panes (cwd, profile, title, buffer) and they come back on launch. `ConptyConnection::ForegroundAgent()` walks a Toolhelp snapshot from the ConPTY client pid to find `claude`/`codex` (image name, or node/bun/deno command line via `_commandlineFromProcess`); `TerminalPaneContent::GetNewTerminalArgs(Persist)` then persists the pane as `<profile cmdline> -NoExit -Command "claude --continue"` / `codex resume --last` (`/k` for cmd, bare command for other shells) with `appendCommandLine:false` and no `sessionId` (the TUI repaints). `_stripResumeCommandline` removes that suffix again so a restored tab whose agent exited persists as a plain shell and never double-wraps. Persistence happens on exit and every 5 minutes; a hard kill loses up to 5 minutes of tab changes.
- Tab search stability: `Tab::GetFocusedProfile` is null-guarded (teardown race), `_updateFilteredTabs` suppresses ListView SelectionChanged reentrancy with a depth counter, and the buffer-text search pass is debounced 250ms behind cheap metadata filtering (`_bufferSearchTimer`). These fixed intermittent crashes when searching while tabs closed/changed focus.
- **Orchestrator (rebuilt 2026-09-04)** is a chat agent *inside the Rust bridge host* (`rust-bridge/src/orchestrator/`), not a Claude Code/Codex TUI in a pane. The old Node `server/orchestrator.ts` + MCP sidecar, the `smoke:orchestrator-rail` script and the native `WebSessionConnection` are gone; the Node adapter answers `/api/orchestrator` with `state:"unavailable"`. It talks to any OpenAI-compatible `/chat/completions` (`llm.rs`: SSE streaming, tool-call assembly across chunks, readable error messages; non-streaming JSON replies also accepted). Defaults: provider `openrouter`, base `https://openrouter.ai/api/v1`, model `anthropic/claude-sonnet-5`, key from `OPENROUTER_API_KEY` (process env, then `HKCU\Environment` / system env in the registry so a key set after launch is still found), reasoning effort `low`. A pasted key overrides the env var; config is `%LOCALAPPDATA%\TerminalWeb\.terminal-web-orchestrator.json`, the shared transcript (bounded to 400 items, streaming items marked cancelled on restart) is `.terminal-web-orchestrator-history.json`. Keys are never returned by the API (`keySource` + masked `keyPreview` only).
- Orchestrator REST/WS: `GET /api/orchestrator[?since=<seq>]` (status + transcript, partial when `since` given), `POST /api/orchestrator/messages {text}` → 202 (409 while a turn runs or with no key), `POST …/cancel`, `DELETE …/messages` (clear), `GET/PUT …/config` (`provider|baseUrl|model|keyEnv|apiKey|reasoning`; `apiKey:""` forgets the manual key), `GET …/models[?refresh=1]` (OpenRouter `/models` normalised to `{id,name,provider,contextLength,promptPrice,completionPrice,tools,reasoning,created}`; `recommended` is `catalog.rs`'s curated coding shortlist — newest tool-capable member per family, `:batch`/`:free` variants excluded — the configured model first; cached 15 min), `POST …/test` (OpenRouter `/key` → label/usage/limit; custom → `/models`). WS global events: `orchestrator` (status without transcript), `orchestrator_item` (one item create/update, keyed by `id` with `rev`), `orchestrator_reset`. `/api/orchestrator/start|stop` return 410.
- Orchestrator context (`context.rs`): every turn rebuilds the system prompt with a live workspace snapshot — per tab: title, id, cwd, git branch (read from `.git/HEAD`, gitdir files resolved), project, shell, detected agent + activity (`working`/`awaiting: <question>`/`idle`), last-output age, and the last 12 screen lines (4 when >12 tabs). History is rebuilt from the transcript (assistant `tool_calls` + tool results, trimmed to 80 items/90K chars, orphan tool results dropped, unanswered calls given a placeholder result). Tools (`tools.rs`, all in-proc): `list_sessions`, `read_session` (scrollback via `vt100` `set_scrollback` windows), `send_input` (bracketed paste when the terminal reports it *or* an agent is detected), `send_keys`, `answer_prompt` (uses `prompt::prompt_response_bytes`), `wait_for_output` (returns when output settles ≥900ms and the agent is not `working`, or after 6s of continued work, max 45s), `create_session` (`launch_terminal`), `close_session`, `rename_session`, `list_projects`, `notify_user`. Session ids also resolve by id prefix or exact title. Max 24 tool rounds per turn, then a forced closing answer. `cargo test live_orchestrator -- --ignored --nocapture` runs a real turn against OpenRouter (needs the key).
- **Agent detection now lives in Rust** (`agents.rs`, ported from the Node `session-input.ts` marks): Claude (`shift+tab to cycle`, `bypass permissions on`, `? for shortcuts`, …) and Codex (`› ` prompt, `ctrl+j newline`, `/approvals`, model status line) scores over the last 60 screen lines, `esc to interrupt` / `• Working (` = busy. Precedence: private OSC handshake > screen > launch command; a screen-recognised agent is *sticky* until the screen ends at a shell prompt (`PS …>`, `$`, `%`, `#`) or another agent wins, because Claude's dialogs hide the footer that identified it. `Session::observe()` runs after output (throttled to 180ms per session) plus a 1s host sweep for sessions that went quiet, writes `agent/agentSource/agentActivity` on the summary and publishes a `session` event only on change — so every client, `input_context` and the orchestrator agree. `prompt::input_context` reports `bracketedPaste: true` whenever an agent is detected (the mirror starts empty after a host restart).
- Web orchestrator panel (`src/components/OrchestratorPanel.tsx`): chat UI over the shared transcript — user bubbles, assistant markdown (`src/lib/markdown.tsx`, dependency-free: fences/headings/lists/inline code/bold/links, never raw HTML), collapsible tool cards (args + result), collapsible reasoning, streaming dots, Stop while running, quick prompts, Clear. Settings view: OpenRouter/custom toggle (base URL for custom), key status line + paste-a-key/forget, env var name, model box + "Recommended for coding" list + search over the whole catalog, reasoning effort, Save/Test. `App.tsx` merges `orchestrator` status events over the existing transcript and upserts `orchestrator_item`s; an assistant item finishing while the panel is closed pulses the rail. After web changes run `bun run build:client` — the Rust `build.rs` embeds `dist/client`.
- Native orchestrator panel (`TerminalPage` XAML `OrchestratorPane`): same chat over REST. `_RefreshOrchestratorStatus` polls `GET /api/orchestrator?since=<seq>` (full reload on open/clear/reconnect or when `itemCount` shrinks) on the 2s bridge tick, plus a 350ms `_orchestratorPollTimer` while a turn is running; rows are keyed by item id and rebuilt only when `rev` changes (`_orchestratorItems`, one `Border` container each). Assistant text renders through `Microsoft::Terminal::UI::Markdown::Builder::Convert`, tool rows are `mux:Expander`s with the result inside, styles are the `Orchestrator*Style` page resources (theme-aware). Enter sends / Shift+Enter newline via `PreviewKeyDown`; the gear button's `Flyout` holds provider/base URL/key/env/model list (`_LoadOrchestratorModels`, search filters the full catalog)/reasoning with Save/Test. `_projectServerRequestDetailed` returns status+body so 409/400 messages from the host reach the error bar.
